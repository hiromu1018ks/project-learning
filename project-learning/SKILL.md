# project-learning: 成果物を学習教材に変換する

## このスキルの目的

ユーザーは superpowers を使って設計 → 実装計画 → 実装と進めるが、AI が成果物を作るため、
「動いたコード」の中身と理由を理解しないまま開発が進みやすい。

このスキルは、設計書・計画書・実装コードを入力として、初学者向けの学習ドキュメントを生成する。
単なる要約ではなく、「なぜこの設計になったのか」「コードの各部分が何をしているのか」を、
背景から順に理解できる教材に再構成する。読者はユーザー自身である。

## 出力物

対象プロジェクトに以下を作成・更新する。

```
LEARNING_STATE.md      学習の進捗記録(このスキルだけが書き換える)
docs/learning/
├── 01-xxxx.md         Claude が執筆する元原稿
├── 01-xxxx.html       変換スクリプトが生成する派生物
└── index.html         教材の一覧ページ(自動生成)
```

html は毎回スクリプトが全再生成するため、手で編集しない(編集しても消える)。
Markdown だけが「元原稿」である。

## 手順

### 0. 前提の確認

`node --version` を実行する。Node がなければ、
「変換には Node.js が必要です。https://nodejs.org からインストールしてください。」
と案内して中断する。

### 1. 進捗の確認

`LEARNING_STATE.md` を読む。

- 存在しなければ、このあとの手順で新規に作成する
- 形式が壊れていると思われる場合は、`LEARNING_STATE.backup-<日付>.md` にコピーを残してから
  新規作成し、バックアップした旨をユーザーに伝える

### 2. 入力の発見

`docs/superpowers/` 配下の設計書(specs)と計画書(plans)を探し、内容を読む。
さらに git log やソースツリーを見て、各設計書に対応する実装コードの所在を把握する。

設計書・計画書がひとつも見つからない場合:
「教材化できる設計書・計画書が見つかりません。」と報告して終了する。
推測で教材を作らない。

### 3. 執筆計画の提案と確認

`LEARNING_STATE.md` の「未執筆のテーマ」と照らし合わせ、
「今回はこのテーマの教材を書きます(理由も添えて)」という提案をユーザーに示し、
確認を得てから執筆に入る。1 回の実行で書くのは 1〜2 テーマまでが目安。
一度に大量に書くと 1 冊あたりの品質が下がるためである。

テーマの単位は「1 つの設計書と、その計画・実装のセット」。
新規ファイルの連番は既存の最大番号 + 1 とする(例: 01, 02 の次は 03)。

### 4. Markdown の執筆

`docs/learning/<連番>-<テーマのスラッグ>.md` に、後述の「文書構成」と「解説レベル制約」に
従って日本語で執筆する。ファイルの冒頭には必ず次の frontmatter を置く
(変換スクリプトが title と date を一覧ページに使う)。

```
---
title: <教材のタイトル>
date: <YYYY-MM-DD>
---
```

他の教材への参照は `<ファイル名>.md` の相対リンクで書く。
変換スクリプトが自動的に `.html` に書き換えてくれる。

### 5. HTML の生成

このスキル自身のディレクトリ(SKILL.md がある場所)にある変換スクリプトを実行する。

```
node <このスキルのディレクトリ>/scripts/build-html.mjs docs/learning
```

スクリプトはすべての md を変換し、html と index.html を全再生成し、件数を報告する。
失敗したファイルがあれば報告されるので、該当 md を修正して再実行する。

### 6. 進捗の更新

`LEARNING_STATE.md` を次の形式で更新する(新規なら作成)。

```markdown
# 学習の進捗(project-learning)

## 対象の成果物
- 設計書: docs/superpowers/specs/xxxx-design.md
- 計画書: (あれば)
- 実装コード: (主な所在)

## 執筆済みドキュメント
| ファイル | テーマ | 対象設計書 | 執筆日 |
|---|---|---|---|
| 01-xxxx.md | ... | ... | YYYY-MM-DD |

## 未執筆のテーマ
- (次に書くべき題材。実装済みだが教材化していない機能など)

## メモ
- (ユーザーからの要望など、次回に引き継ぎたいこと)
```

最後に、生成した教材のパスと「index.html をブラウザで開くと読める」ことをユーザーに伝える。

## 文書構成(各教材のテンプレート)

1. 今回何を作ったのか
2. なぜその機能が必要なのか
3. 全体の設計
4. 設計上の重要な判断
5. 実装までの計画
6. 実際のコード構成
7. コードがどのように動くのか
8. 使用している技術・パターンの解説
9. 設計と実装の対応関係
10. 初学者が覚えておくべきポイント
11. ことばのまとめ(その回で登場した用語の簡単な辞書)

項目はテーマに合わせて統合・省略してよいが、順序は「背景 → 設計 → 実装 → まとめ」を守る。
読者がまだ知らない概念を、使う場面より先に説明してはいけないためである。

## 解説レベル制約(最重要)

読者は「プログラミング経験ほぼゼロの初学者」である。以下を守る。
守れないまま書き上げた教材は、読者にとって読めない文章になる。

1. 専門用語は初出時に必ず平易な定義を併記する。
   例: 「リポジトリ(= 変更履歴つきのプロジェクト保管場所)」
2. 例え話(郵便・料理などをプログラミングにたとえる説明)は使わない。
   ユーザー自身が「例え話はわかりづらい」と明言しているため。
3. 1 文は 40 文字を目安とし、1 文 1 情報を守る。
4. コードは 3〜10 行程度の小さい断片に分け、直後に各断片が「何をしているか」を説明する。
   ファイル全体を長々と貼らない。
5. 説明の順序は「何が起きるか → なぜそうなるか → どこで使われているか」の順。
6. 読者に要求する前提知識は「ファイルとフォルダ」「ブラウザでページを開く」までとする。
   それ以上の概念は教材の中で補足する。
7. 深い内部動作・最適化・歴史的経緯は原則省略する。
   どうしても必要な場合のみ「ここはまだ理解しなくてよい」と断ってから載せる。
8. 文体は平易な言葉を選び、漢語よりも日常語を優先する。
9. 処理の流れ・全体構造・対応関係の説明では、文章だけに頼らず図や表を積極的に使う。
   図はコードブロックの中に文字と罫線で描くテキスト図、表は Markdown の表とする
   (どちらも変換スクリプトがそのまま HTML 化できる形式だから)。

## エラー時の挙動

| 状況 | 挙動 |
|---|---|
| Node が無い | 手順 0 で検知し、案内を表示して中断 |
| 設計書・計画書が無い | 「見つかりません」と報告して終了(推測で作らない) |
| LEARNING_STATE.md が壊れている | バックアップを残して初期化し、通知 |
| md の変換に失敗 | スクリプトの報告を見て該当 md を修正し、再実行 |
