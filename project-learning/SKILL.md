# project-learning: 成果物を walkthrough 式の学習教材に変換する

## このスキルの目的

ユーザーは superpowers を使って設計 → 実装計画 → 実装と進めるが、AI が成果物を作るため、
「動いたコード」の中身と理由を理解しないまま開発が進みやすい。

このスキルは、実装コードを読み、**利用者の操作ごとに章を切った解説書**を生成する。
各章では、その操作で動くコードを実行の順番どおりに追う。
単なる要約ではなく、「この操作の裏で何が起き、なぜそうなっているのか」を、
読みながらたどれる教材にする。読者はユーザー自身である。

## 解説書の形式

章の単位は「利用者が行う操作1つ」(登録する・一覧を出す・読み込む など)である。
操作をきっかけにコードを読むほうが、設計書の要約を読むより理解が進むためである。

各章は同じ 4 パートで構成し、章どうしは「前章の続きから始まる」。
すべて読み終えたとき、1 冊の解説書としてつながることを目標にする。

## 出力物

対象プロジェクトに以下を作成・更新する。

```
LEARNING_STATE.md      学習の進捗記録(このスキルだけが書き換える)
docs/learning/
├── 00-junbi.md        章0: この解説書の読み方(初回のみ)
├── 01-xxxx.md         章1以降: 操作ごとの章(元原稿)
├── NN-xxxx.html       変換スクリプトが生成する派生物
└── index.html         目次ページ(自動生成)
```

html は毎回スクリプトが全再生成するため、手で編集しない(編集しても消える)。
Markdown だけが「元原稿」である。

## 手順

### 0. 前提の確認

`node --version` を実行する。Node がなければ、
「変換には Node.js が必要です。https://nodejs.org からインストールしてください。」
と案内して中断する。

### 1. 進捗の確認

`LEARNING_STATE.md` を読む。

- 存在しなければ、このあとの手順で新規に作成する
- 中身が旧形式(「執筆済みドキュメント」を主にしたテーマ単位の記録)や
  壊れた形式と思われる場合は、`LEARNING_STATE.backup-<日付>.md` にコピーを残してから
  新形式で初期化し、バックアップした旨をユーザーに伝える
  (新形式は本書末尾の「LEARNING_STATE.md の形式」を参照)

### 2. 操作の列挙

実装コードを読み、「利用者が行える操作」を列挙する。

出典は、メニュー項目・コマンド一覧・画面・ルーティングなど、
利用者から見える挙動の単位である。操作は利用者の言葉で表現する
(例: 「支出を1件登録する」「一覧を出す」)。

- コマンドラインアプリの各コマンド(例: `todo add` / `todo list`)も操作として数える
- 設計書・計画書(`docs/superpowers/` 配下)があれば「なぜ」の材料として読む。
  ただし必須の入力ではない。無くてもコードから進められる
- 操作という概念が無い対象(ライブラリなど)は、「代表的な使い方1つ」を1操作とみなす

実装コードが見つからない場合(設計書だけある場合を含む):
「教材化できる実装が見つかりません。」と報告して終了する。
実装が無いものは追跡できない。推測で教材を作らない。

### 3. 章リストの提案と承認

**初回(章が1つもない)の場合:**
章0(導入)と、操作ごとの章を番号付きで一覧にして提案する。

```
章0 この解説書の読み方とプロジェクトの形
章1 起動して使い方を表示する
章2 タスクを追加する
章3 タスクの一覧を出す
章4 タスクを完了にする
```

ユーザーの承認を得てから LEARNING_STATE.md に章リストを記録する。
初回は承認後に、**章0 と最初の操作章の 2 つを書いてよい**。
章0 はコードの追跡を含まない軽い導入であるためである。章1 以降は 1 回 1 章を守る。
先に全部の章立てを固めておくことで、章番号の割り振りと「次に何を書くか」が
確定し、複数回に分けた執筆でも解説書がつながるからである。

**継続(章リストがある)の場合:**
未執筆の章から「今回はこの章を書きます(理由も添えて)」と提案し、確認を得てから執筆に入る。
**1 回の実行で書くのは 1 章である。** 大きな操作でも最大 2 章まで。
一度に大量に書くと 1 章あたりの品質が下がるためである。

**前回から開発が進み、新しい操作が増えていた場合:**
章リストへの追加を提案し、承認を得てから末尾の番号を割り当てる。

### 4. 章の執筆

続きの章を書くときは、まず前章の「実行の追跡」の最終 Step を読む。
LEARNING_STATE.md の「再開地点」と照らし合わせ、前章のどこから続くかを確定してから書き始める。
つなぎ目がずれた解説書は、読者にとって地図が壊れたのと同じである。

`docs/learning/<章番号の2桁>-<スラッグ>.md` に執筆する(例: `01-kidou.md`)。
スラッグは短いローマ字とする。ファイルの冒頭には必ず次の frontmatter を置く
(変換スクリプトが title と date を目次ページに使う)。

```
---
title: 章1 起動して使い方を表示する
date: <YYYY-MM-DD>
---
```

他の章への参照は `<ファイル名>.md` の相対リンクで書く。
変換スクリプトが自動的に `.html` に書き換えてくれる。

#### 章0(初回のみ作る導入)

| 内容 | 説明すること |
|---|---|
| この解説書の読み方 | 操作を選び、その操作で動くコードを実行順に読む形式であること。「プログラムはファイルを上から順に読んでも動きが分からない」ため、章と節が実行の移動順に並んでいること |
| 各章の構成 | 4 パートの紹介と、各章が前章の続きから始まること |
| コードの載せ方 | 断片+行ごとの表であること。説明済みのものは「(章Nで説明済み)」とだけ書くこと |
| 頻出用語の定義表 | 全章を通じて頻出する用語の表 |
| プロジェクトの形 | フォルダ構造の `text` 図 |

#### 章1以降(4 パート固定)

章の冒頭に必ず、前章とのつなぎ目を 1 行書く。

```markdown
# 章2 タスクを追加する
(章1 の Step 5 で add が入力された直後から始まります)
```

そのあと、次の 4 パートを見出し付きで入れる。

```
## 1. この章で追う操作
## 2. 流れの全体図
## 3. 実行の追跡
## 4. この章で登場したファイル
```

| パート | 内容 |
|---|---|
| 1. この章で追う操作 | 利用者の操作を番号付きで並べる(例: ①`todo add 买い物` を入力 ②「追加しました」と出る) |
| 2. 流れの全体図 | 呼び出しのつながりを `text` 図で示す。分岐がある場合は、本章で追う道と他の道の行き先(「→ 章9 で追う」など)を明示する |
| 3. 実行の追跡 | Step 1, 2, ... の順で追う。各 Step は下の型に従う |
| 4. この章で登場したファイル | 表: ファイルパス \| この章で分かったこと |

実行の追跡の各 Step は、次の型で書く。

````markdown
Step N 〈いま何をしているか〉

(平易な文で、この Step で起きることを1〜2文)

```java
(コード断片。10 行以内)
```

| 行 | やっていること |
| --- | --- |
| 1〜2 | ...(断片の中での行番号で書く) |

(なぜそうなっているか: 疑問が湧く箇所にだけ、短く)
````

#### コードの載せ方

- コードは実ファイルからそのままコピーする(手で書き換えない)
- 1 断片は **10 行以内**。直後に「行ごとのやっていること」の表を付ける
  (表の行番号は断片の中での番号とする。手順 5 の点検で必ず確認する)
- import 文など説明対象にならない定型は省略し、「(import 6行)」のように 1 行で示してよい
- クラス全体を見せたい場合は、断片を分割して順番に並べる。1 ブロックで丸ごと載せない
  (10 行を超える断片は、超過がそのまま出荷されてしまう。初回開発時に実際に起きた)
- 過去の章で説明済みの関数・メソッドは、説明を繰り返さない。
  見たことのある道を通るときは「(章Nで説明済み)」とだけ添える。
  まだ見ていない道(別の分岐・ファイルがあるため成功する場合など)を通るときは、
  断片をもう1度載せて、見たことのない部分だけを説明してよい。
  そのときも断りは必須で、書式は必ず「章Nで説明済み」で始める
  (例: 「(章1で説明済み。今回は成功する道)」。
  「説明済み」の表記をそろえることで、読者も点検も説明の重複を見つけやすくなるため)
- コードには言語タグ(java など)を付ける

#### 図と表

- 図はコードブロック内のテキスト図で、**必ず `text` タグを付ける**
  (コードとの区別がタグだけで済み、点検を機械的にできるため)
- 図は行数制約の対象外とする。見やすさを優先する
- 対応関係・比較は文章よりも表を優先する

#### 「なぜ」の扱い

「なぜこの設計になったのか」の専用セクションは作らない。
代わりに、追跡の途中で「なぜこうなっているのか」という疑問が自然に湧く箇所で、短く添える。
材料は設計書・計画書・git log の判断記録であり、無い場合は推測で理由を作らない。

#### 章が長くなりすぎたら

1 章を書き進めた結果、明らかに長すぎると判断したら、追跡の自然な区切りで章を分ける。
以降の章番号を繰り下げ、LEARNING_STATE.md の章リストを更新し、ユーザーに報告する。

### 5. 点検(章を書き終えるたびに)

超過や欠落は読者には見抜けないため、出荷前に必ず確認する。

| # | 確認すること | 方法 |
|---|---|---|
| 1 | コード断片が 10 行以内か | awk 点検(下記) |
| 2 | すべての断片の直後に「行ごとの表」があるか | 目視 |
| 3 | 図に `text` タグ、コードに言語タグが付いているか(無タグのブロックが無いか) | awk 点検(下記) |
| 4 | 章の冒頭に前章とのつなぎ目が書かれているか | 目視 |
| 5 | パート1の操作手順が、パート3の追跡ですべて通過しているか | 目視 |
| 6 | 初出の専門用語に定義があるか | 目視 |

コード断片の行数点検(コードのみを数え、`text` 図と無タグを除外する):

```
awk '/^```/{if(f){if(t&&n>m)m=n;f=0}else{f=1;n=0;t=($0~/^```[a-zA-Z]/&&$0!~/^```(text|plain)/)?1:0}next} f{n++} END{print m+0}' docs/learning/*.md
```

出力が 10 を超えたら、超えている断片を処理のまとまりで分割し、
分割した各部分の間に「何をしているか」の説明を挟む。

タグ規約の点検(無タグで開かれたブロックの個数。0 であれば規約どおり):

```
awk '/^```/{if(f){f=0}else{f=1;if($0!~/^```[a-zA-Z]/)u++}next} f{n++} END{print u+0}' docs/learning/*.md
```

0 でなければ、図には `text` タグを、コードには言語タグを付け直す。

### 6. HTML の生成

このスキル自身のディレクトリ(SKILL.md がある場所)にある変換スクリプトを実行する。

```
node <このスキルのディレクトリ>/scripts/build-html.mjs docs/learning
```

スクリプトはすべての md を変換し、html と index.html を全再生成し、件数を報告する。
失敗したファイルがあれば報告されるので、該当 md を修正して再実行する。

### 7. 進捗の更新

LEARNING_STATE.md を「LEARNING_STATE.md の形式」どおりに更新する。
特に「再開地点」は、**章を書き終えるたびに必ず更新する**。
ここは次回の執筆が前章のどこから始まるかを保証する唯一の記録である。

最後に、生成した章のパスと「index.html をブラウザで開くと読める」ことをユーザーに伝える。

## 解説レベル制約(最重要)

読者は「プログラミング経験ほぼゼロの初学者」である。以下を守る。
守れないまま書き上げた教材は、読者にとって読めない文章になる。

1. 専門用語は初出時に必ず平易な定義を併記する。
   例: 「リポジトリ(= 変更履歴つきのプロジェクト保管場所)」
2. 例え話(郵便・料理などをプログラミングにたとえる説明)は使わない。
   ユーザー自身が「例え話はわかりづらい」と明言しているため。
3. 1 文は 40 文字を目安とし、1 文 1 情報を守る。
4. 説明の順序は「何が起きるか → なぜそうなるか → どこで使われているか」の順。
5. 読者に要求する前提知識は「ファイルとフォルダ」「ブラウザでページを開く」までとする。
   それ以上の概念は教材の中で補足する。
6. 深い内部動作・最適化・歴史的経緯は原則省略する。
   どうしても必要な場合のみ「ここはまだ理解しなくてよい」と断ってから載せる。
7. 文体は平易な言葉を選び、漢語よりも日常語を優先する。
8. 処理の流れ・全体構造・対応関係の説明では、文章だけに頼らず図や表を積極的に使う。

## LEARNING_STATE.md の形式

```markdown
# 学習の進捗(project-learning)

## 対象の成果物
- 実装コード: (主な所在)
- 設計書・計画書: (「なぜ」の材料。なくても可)

## 章リスト(承認済み)
| 章番号 | 操作 | ファイル | 執筆日 |
|---|---|---|---|
| 0 | この解説書の読み方とプロジェクトの形 | 00-junbi.md | YYYY-MM-DD |
| 1 | (操作名) | (未執筆) | |

## 再開地点(次に書く章はここから始める)
- 章2 は「章1 の Step 5 で 1 が入力された直後」から

## メモ
- (次回に引き継ぎたいこと)
```

## エラー時の挙動

| 状況 | 挙動 |
|---|---|
| Node が無い | 手順 0 で検知し、案内を表示して中断 |
| 実装コードが見つからない | 「教材化できる実装が見つかりません」と報告して終了(推測で作らない) |
| コードが読めず操作の候補を挙げられない | ユーザーに候補を尋ねてから進める |
| LEARNING_STATE.md が壊れている・旧形式 | バックアップを残して新形式で初期化し、通知 |
| md の変換に失敗 | スクリプトの報告を見て該当 md を修正し、再実行 |
